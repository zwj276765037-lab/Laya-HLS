## Recovery sequence and boundaries

`tb/recover_reports_from_dcp.tcl` accepts only the exact sealed DCP path and a single named fresh reports sibling. It checks both the DCP and unchanged Ws Tcl SHA256 before creating that directory. It calls `open_checkpoint` once, checks zero blackboxes and exactly one `ap_clk`, then writes utilization, hierarchical utilization, clocks, verbose timing checks, timing summaries with and without unconstrained paths, and the original full Ws reports. The supported `report_timing_summary -report_unconstrained -max_paths 100` replaces only the incompatible diagnostic command; it does not imply any routed timing or Fmax result. The source has no `open_project`, `launch_runs`, `synth_design`, IP generation, implementation or checkpoint write command.

The planned report root is `ooc_v1/runs/top_dcp_report_recovery_v1_reports`, with a separate future control/CWD sibling. Both must be absent before a later execution gate; Vivado log and journal must be explicitly directed into control, not into the sealed clone or old reports. Any report error must preserve the DCP and partial outputs without rerunning synthesis. The report stage requires a new Astra-reviewed finite budget and heavy-tool slot; none is granted by this source packet.

The eight Ws logical banks each require 20,992 words × 16 bits, including addresses 16,384–20,991. Physical primitive count alone cannot establish that depth. The later reviewer must map storage-bit ownership and effective capacity per bank, then trace logical `address0` read and `address1` write bits 0–14 through decode, WE and read selection to the actual primitives. The recovered reports are evidence for that review, not automatic acceptance. Timing is synthesis/OOC diagnostic only; no placement, routing, achieved 150 MHz, board behavior or 50 ms claim follows.
