# Preloaded Attention source-check IR comparison

Read-only trace, 2026-10-08. This compares the failed preloaded linked stage-5 IR with the successful D2-I linear linked stage-5 IR. No source correction or synthesis was performed for this trace. The eight decoded IR files in this directory are derived from the already generated bitcode and are bound in `trace_evidence.json`.

## The first distinct escaped pointer

Both linked IRs declare `FullMemory` as 13 alternating pointer/capacity pairs (208 bytes) and `Controller` as two pointers and control fields (32 bytes). The types alone therefore cannot explain why one source check passes. Both tops allocate a `FullMemory`, assign external port pointers to fields, and eventually put its address in `Controller.memory`.

The preloaded top stores `%memory` into `%controller.memory` at `preloaded_a.g.ld.5.gdce.bc.ll:27957-27959` **before** its first `full_parse_request` call at line 27990. Its first use of the controller across a wrapper boundary is `fail(..., Controller&, false)` at line 27982, also before parsing; the top has 25 `fail` calls. `fail` survives as a separate IR function at line 29736 and calls `Controller::invalidate_incomplete()` through the passed `%controller` at line 29762. Thus the nested address chain `top m_axi pointer -> FullMemory field -> FullMemory* in Controller -> Controller* passed to fail` remains explicit at source checking. Four `run_task(FullRuntime&, FullMemory&, ...)` calls are another aggregate-bearing path, but occur later.

The successful D2-I linear top first calls `full_parse_request` at `linear_a.g.ld.5.gdce.bc.ll:33397`, then stores `%memory` in `%controller.memory` at line 33448. Its error paths call `Controller::invalidate_incomplete()` directly in the top at lines 33631 and 33686; there is no `fail(..., Controller&)` call. It does still call `full_write(memory, ...)` and production Controller methods. `full_parse_request`, `full_check_model_header`, `full_read`, and `full_write` definitions with `FullMemory&` also survive in the linear linked IR. This narrows the first *distinct* pointer escape to the preloaded helper call and its earlier control-flow placement; it does not prove which optimizer transformation or HLS source rule fails.

The preloaded run reported 50 `HLS 214-134` pointer-to-pointer errors, beginning at `full_check_model_header` (`hls/common/laya_full_memory.cpp:219:24`), followed by `full_parse_request`, `full_read`, `full_write` and the wrapper. It stopped before scheduling or RTL. See the immutable failure evidence (SHA256 `03d902534bafe52afbc77e9ad6b0a0261b229632f7323ed935bc9bcea05a6047`). The D2-I v3 run reached generated RTL, so the common aggregate and functions can be accepted in at least that call topology.

## Falsifiable correction proposal for Astra review

In a new isolated preloaded source identity, retain the same production Controller, BEGIN/RUN semantics, observed fields, owner operations, and numeric task order. Two local equivalents can test the wrapper boundary:

1. Preferred, structurally decisive: remove `Controller&` from the out-of-line `fail` helper. At each top-level `close_pending=true` branch, capture the first error `Check`, call `controller.invalidate_incomplete()` directly, record cleanup status/detail, call the same report logic, then close `pending.valid`; `close_pending=false` branches only report. The report-only helper may accept the two `Check` values but no Controller or FullMemory reference. This mirrors D2-I's direct cleanup. The order must remain first error capture -> cleanup -> report with the pending pair still visible -> pending close. The new linked IR should contain no `Controller* -> fail` call.
2. Smaller source diff but weaker prediction: mark the existing `fail` helper for local forced inlining while preserving its body and call sites. If the HLS front end honors inlining before its pointer check, the linked or checked IR should have no surviving `fail(..., Controller&)` call. If it ignores the hint or checks earlier, the escape remains and the same rejection is expected. This candidate changes no runtime semantics but its success depends on pass order.

Moving Controller construction after parsing while still passing its reference to `fail` does **not** independently remove the escape; it should be a separate experiment only if evidence later points to call ordering. Neither variant changes `FullMemory` or the production Controller. A source diff and CPU/CSim equivalence review must precede a newly gated synthesis attempt.

Prediction: if the helper escape is the blocker, equivalent CPU/CSim tests pass and the new HLS source check no longer emits the same pointer-to-pointer errors; if the decisive call-site variant removes the escape but those errors persist, the hypothesis is falsified, and the next IR comparison should inspect the four `run_task` aggregates and the controller-before-parse placement independently. No production edit or unchanged retry is justified by this trace alone.
